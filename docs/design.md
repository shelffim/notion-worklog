# 설계

AI 코딩 에이전트(Claude Code, Codex CLI)의 세션을 Notion 테이블의 행 하나로 기록한다.
이 문서는 동작 원리와, 실제로 부딪혀 보고 정한 결정들을 남긴다.

## 1. 핵심 결정

| 항목 | 결정 | 근거 |
|---|---|---|
| 기록 단위 | 세션 1개 = Notion 페이지(행) 1개 | 목록이 깔끔하고 세션 단위로 돌아보기 쉽다 |
| 훅 시점 | `Stop`(매 응답 끝) + `SessionEnd`(세션 끝) | 세션이 강제 종료돼도 기록이 남는다. 트랜스크립트가 비동기로 쓰여 `Stop` 시점에 마지막 턴이 아직 없을 수 있으므로 `SessionEnd` 가 마저 채운다 |
| 토큰 비용 | 0 | 훅은 에이전트 밖의 파이썬 프로세스다. LLM 을 부르지 않는다 |
| 훅 출력 | stdout 무음, 항상 exit 0 | 출력이 세션 컨텍스트로 돌아가면 매 턴 토큰이 쌓인다. Claude Code 는 `{...}` 출력을 JSON 으로 파싱하고, Codex 는 `Stop` 의 비JSON 출력을 오류로 본다 |
| API 버전 | `2022-06-28` 고정 | `2025-09-03` 은 데이터베이스를 data source 로 재구성해 생성·조회 방식이 다르다 |
| 원문 첨부 | 세션 전체 원문을 `session.md` 로 항상 첨부 | 인라인 블록은 1900자에서 잘리고, API 앞단 필터가 일부 문자열을 거부할 수 있다. 첨부는 둘 다 겪지 않는다 (§4) |
| 거르는 세션 | 작업 폴더가 임시 폴더인 세션, `NOTION_WORKLOG_DISABLE` 이 켜진 세션 | 훅은 전역 설정이라 에이전트가 훅을 시험하려고 띄운 `claude -p` 까지 기록한다 (2026-10 실제로 테스트 대화 6건이 섞였다). 헤드리스 여부로 거르면 하네스의 단계 실행 같은 진짜 자동화 작업까지 빠진다. 테스트는 일회용 프로젝트가 필요해 거의 항상 임시 폴더에서 돌므로 작업 폴더로 거른다 |
| 필터 우회 | 하지 않는다 | 남은 방법이 전부 "보안 필터가 문자열을 못 알아보게 만드는 것"이다. 임의의 대화에 무차별로 도는 훅에 넣을 코드가 아니다 |

## 2. 구조

```
src/notion_worklog/
  cli.py        진입점. hook(무음·exit 0·임포트 가드), setup/uninstall 로 분기
  setup_cmd.py  setup / uninstall 대화형 흐름
  schema.py     URL → 데이터베이스 찾기(인라인 테이블 포함), 열 갖추기
  install.py    ~/.claude/settings.json, ~/.codex/hooks.json 에 훅 등록·해제
  sync.py       에이전트와 무관한 동기화: 페이지 찾기/만들기, 증분 append, 첨부, 잠금
  notion.py     Notion REST 래퍼, 속성/블록 빌더, 배치 분할
  state.py      세션 → 페이지·워터마크 캐시 (원자적 쓰기, 30일 정리)
  transcript.py 에이전트 공통: jsonl 읽기, 시각 변환, 대체 제목, session.md 문서
  text.py       ko/en 문자열 (열 이름, 머리글, 마커)
  agents/
    claude.py   Claude Code 세션 jsonl → 대화
    codex.py    Codex rollout jsonl → 대화
```

어댑터 인터페이스(`agents/__init__.py`): `NAME`, `SHORT`, `read_entries`, `started_at`,
`project_name`, `title`, `conversation`. 새 에이전트는 이 모듈 하나와 `install.py` 의 등록
방식만 더하면 된다.

## 3. 데이터 흐름

```
에이전트 응답 종료
  └→ 훅 (stdin JSON: session_id, transcript_path, cwd, hook_event_name)
       ├─ 0. 거를 세션(임시 폴더 cwd, NOTION_WORKLOG_DISABLE)이면 곧바로 끝  [네트워크 없음]
       ├─ 1. 어댑터가 트랜스크립트 파싱 → 제목/시각/프로젝트/대화       [네트워크 없음]
       ├─ 2. 페이지 찾기: 캐시(state.json) → 미스면 세션ID 로 DB 검색 → 없으면 생성
       ├─ 3. 워터마크 이후의 새 메시지만 블록으로 append (메시지 단위 배치)
       │     배치 하나 성공할 때마다 워터마크 즉시 저장
       ├─ 4. session.md 첨부 — 첫 첨부 / SessionEnd / 거부 발생 시 갱신
       └─ 5. 항상 exit 0, stdout 무음, 실패는 error.log
```

### 에이전트별 차이

| | Claude Code | Codex CLI |
|---|---|---|
| 트랜스크립트 | 세션 jsonl. 엔트리마다 `uuid` | rollout jsonl. `response_item`/`message` 의 `payload.id` (옛 형식은 id 가 없어 줄 번호를 쓴다) |
| 거르는 것 | 슬래시 커맨드 찌꺼기, `isMeta`, 시스템 알림 태그, 도구 입출력 | `<environment_context>`, `<recommended_plugins>`, `# AGENTS.md instructions`, developer 메시지, 도구 호출·추론 |
| 제목 | `aiTitle` → 마지막 프롬프트 → 첫 프롬프트 첫 줄 → 대체 제목 | 첫 프롬프트 첫 줄 → 대체 제목 |
| 훅 등록 | `async: true`, timeout 120 | 동기 + `--detach` (아래) |

**Codex 는 `--detach` 를 쓴다.** Codex 는 끝날 때 백그라운드(async) 훅을 죽인다 —
`codex exec` 실측에서 async `Stop` 훅은 기록을 하나도 남기지 못했다. 또 `SessionEnd` 는
동기 실행에 최대 3초다. 그래서 Codex 훅은 동기로 불려 페이로드를 새 세션
(`start_new_session`)의 자식 프로세스에게 넘기고 곧바로 돌아온다. 일은 자식이 한다.

Codex 는 신뢰(trust)하지 않은 훅을 실행하지 않는다. 사용자가 `/hooks` 에서 한 번 신뢰해야
한다.

## 4. Notion API 앞단 필터

2026-09 실측: `append` 가 받는 403 중에는 Notion 이 아니라 앞단 Cloudflare 의 것이 있었다
(본문이 JSON 에러가 아니라 `Attention Required! | Cloudflare` HTML). 원인을 크기·속도로
세 번 잘못 짚었고, 블록을 하나씩 보내 보고서야 **`<script` 문자열이 든 블록 하나**만
언제나 실패한다는 것을 찾았다. 큰 배치가 더 자주 실패한 건 그 블록을 포함할 확률이
높아서였다. (이 규칙은 Notion 쪽 사정으로 바뀔 수 있다 — 2026-10 재검증 때는 통과했다.)

대응은 두 겹이다.

1. **거부된 블록은 마커로 대체한다.** 청크가 Cloudflare 403 을 받으면 반으로 쪼개
   재귀적으로 재시도해 문제 블록을 이웃과 분리한다. 블록 1개에서도 막히면 그 블록만
   마커 문단으로 바꿔 보낸다. 진짜 Notion 403(JSON)은 재시도하지 않는다. 총 시도는
   `max(40, 3n)` 으로 묶는다 — 완전 이진 분할의 최악 비용이 정확히 `3n-1` 이다.
2. **세션 원문을 `session.md` 로 첨부한다.** 파일 업로드 API 는 필터를 타지 않는다
   (`<script` 원문을 올렸다 내려받아 바이트 단위로 일치함을 확인). 마커는 "원문은
   session.md 에 있다"고 가리키므로, 거부가 생긴 턴에는 간격 없이 곧바로 첨부를
   갱신하고, 그 의무는 업로드가 실패해도 다음 발화로 넘어가도록 `state.json` 에 남긴다.

제목도 대화에서 오므로 같은 이유로 막힐 수 있다. 그때는 대화가 한 글자도 섞이지 않은
대체 제목(`{프로젝트} 세션 HH:MM`)으로 한 번만 다시 보낸다.

## 5. 증분 기록과 재개

- 한 요청에 블록 100개까지라, 배치를 **메시지 단위**로 묶는다. 블록 단위로 자르면
  경계가 메시지 중간에 떨어져 저장할 워터마크가 없어진다.
- 배치 하나가 성공할 때마다 워터마크를 즉시 저장한다. 그래야 부분 실패가 진행을
  보존하고 다음 발화가 나머지만 잇는다.
- 요청 바디는 8KB 안팎으로 묶는다(UTF-8 로 직렬화한 실제 바이트로 잰다). 배치가 작아야
  쪼개기가 문제 블록을 빨리 분리하고, Notion 자체 한도(~190KB)에도 여유가 있다.
- 요청 간격은 0.5초 — Notion 은 통합당 초당 약 3요청을 허용한다.

### 결과를 모르는 append

읽기 타임아웃은 "반영되지 않았다"는 뜻이 아니다. Notion 이 블록을 이미 붙였는데 응답만
늦을 수 있고, 그대로 다시 보내면 메시지가 두 번 실린다 (실제 발생). SIGKILL 도 같은
모양이다.

- 배치를 보내기 **전에** `append_pending` 을 `state.json` 에 남긴다. 성공해 새 워터마크를
  쓰면 함께 사라진다.
- 다음 발화가 이 표시를 보면 본문을 읽어, 워터마크까지의 예상 블록 뒤에 이어진 블록이
  보낼 블록의 앞부분과 정확히 같으면 그만큼 건너뛴다(마커는 1:1 대체이므로 무엇과도
  같다고 본다). 어긋나면 건너뛰지 않고 다시 보낸다 — 중복이 유실보다 낫다.

## 6. 동시성

- **같은 세션의 동시 발화**(`Stop` 이 아직 도는 중에 `SessionEnd`)는 페이지를 두 개
  만들 수 있다. 세션ID 로 키를 만든 `O_EXCL` 잠금으로 직렬화한다. 진 쪽은 몇 초
  기다렸다가 못 얻으면 물러난다. SIGKILL 로 남은 잠금은 나이(180초)로 회수한다.
- **다른 창의 캐시 항목 덮어쓰기**를 막으려고, 저장 직전에 파일을 다시 읽어 이 세션
  항목만 병합해 쓴다(임시 파일 + `os.replace`).
- 캐시를 잃어도 세션ID 검색으로 같은 페이지를 다시 찾으므로 행이 둘이 되지 않는다.
  이때는 본문을 비우고 처음부터 다시 쓴다.

## 7. 보안

- 토큰은 `~/.notion-worklog/token`(600)에만 둔다. 에이전트 설정 파일의 환경변수 블록에
  넣지 않는다 — 그 값은 모든 셸 호출에 주입돼 대화 기록으로 새기 쉽다.
- `error.log` 에 토큰이나 응답 본문 전체를 쓰지 않는다.
- setup 은 토큰을 화면에 출력하지 않는다. 모든 확인이 끝난 뒤에만 저장한다.
- 테스트 픽스처는 전부 합성 데이터다.

## 8. 범위 밖

- LLM 요약 — 원문이 남으므로 나중에 소급 생성할 수 있다.
- Windows, 데이터 소스가 여러 개인 데이터베이스, 다른 에이전트.
